我们导师的项目里有个记账类的后端，一直用传统的"直接改当前余额"那套存数据，出过几次对不上账、又查不清是谁在哪一步改的问题。这学期想借机让我做一个以事件溯源加读写分离为骨架的小框架，把"改状态"彻底换成"记事件"，配一个简单的管理后台能看能操作。核心就一个聚合概念，比如账户：所有对它的变更都以一条条不可变的事件形式按顺序追加进事件流，绝不原地修改也绝不删除历史；聚合在任意时刻的当前状态，是把它的事件从头依次回放、逐条应用到一个初始状态上重建出来的。

后端要立住这么几条硬规则。事件一旦落库就不可更改，只能往后追加，每条事件在自己聚合内有严格递增且连续的版本号；提交一条新事件时要带上客户端认为的当前版本，如果和服务端实际最新版本不符（说明中间有人先写了），就判为并发冲突拒绝这次追加，让调用方拿最新状态重试，避免两路写把版本写乱。为了不必每次都从第一条事件放到最后，要支持给聚合打快照：快照记录到某个版本为止重建出的状态，之后重建时从最近的快照往后放剩余事件即可，且无论走不走快照、快照打在哪个版本，重建出的最终状态必须一模一样。读模型这边和写模型分开：有一个投影把事件流消费成便于查询的视图（比如账户列表和余额汇总），投影必须能从头重放整条事件流重新算出来，且重放的结果要和增量消费得到的结果完全一致——这条投影一致性是整个框架最要命的不变量，我会重点盯。另外要能对某个聚合做完整的事件重放，按版本区间取出它经历过的事件序列。

校验和边界要处理清楚：对不存在的聚合追加要么按新建处理、要么明确拒绝（选一种并说清）；版本号不连续、快照版本超出已有事件范围、并发版本不匹配这些都要给出明确的错误响应；金额之类的业务约束（比如账户余额不能被取成负数）在生成事件前校验，不合法就不产生事件。这几条我会写成自动化测试逐条锁死：同一聚合并发提交同版本只能成功一条、另一条报冲突；带快照重建与不带快照全量重放得到的状态逐字段相等；投影全量重算与增量消费结果一致；事件流一旦写入其内容和顺序在后续操作中不被改动。

前端用 React 做一个朴素的管理后台就够，不需要画布或拖拽：一个页面列出所有聚合及其当前状态，点进去能看到该聚合完整的事件时间线和每条事件的版本，能触发追加一条新事件、能手动打一次快照、能对读模型做一次全量重放并把结果显示出来。所有数据都来自后端接口，前端不自己算业务。后端跑在 Node.js 20 上、用 TypeScript 编写，HTTP 层可选 Fastify 或 Express，事件与快照落库到 PostgreSQL 16。请把事件存储、聚合重建、快照、读模型投影、并发版本控制、业务校验、HTTP 接口和前端各自拆成独立模块与文件，别把核心逻辑堆在一处。附自动化测试覆盖上面那几条不变量，尤其是投影一致性和快照重建等价。用 Docker Compose 把前端、后端和数据库编排起来，构建后对外暴露页面与接口即可使用。范围就限定在事件溯源、快照重建和读写分离这套机制本身，不做权限后台，也不做复杂的多聚合事务。
